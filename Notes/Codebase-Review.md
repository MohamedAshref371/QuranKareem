# Quran Kareem: codebase review

Reviewed on 2026-11-09. This is a static review of the source, project files, and a small read-only sample of the bundled SQLite schemas. I did not run the application, benchmark it, change code, or validate the behavior on different Windows displays. Performance and user experience observations below are therefore code-based hypotheses unless stated otherwise.

## What the project does today

This is a .NET Framework 4.8 WinForms application. The main window combines Quran navigation, image/text/font rendering, recitation, word highlighting, tafsir and translations, search, color rules, audio downloads and timing edits, verse splitting/combining, SRT output, and video-editor template generation. The Quran data is stored in separate SQLite databases; the bundled text and picture databases have indexes for common page, quarter, and surah/ayah lookups. These are useful foundations to retain even if the application and database formats are redesigned.

The main limitation is that one form coordinates almost every feature, while the Quran classes combine data access, mutable navigation state, rendering, and UI controls. This makes a small feature change likely to affect navigation, playback, and display at once. Breaking compatibility with old versions is acceptable for a future redesign, but the content and timing data still need explicit preservation and validation.

## Highest-priority findings

| Priority | Finding and evidence | User impact / later direction |
| --- | --- | --- |
| P0 | The download queue is a static `LinkedList` and `current` field changed by UI handlers and `Task.Run(DownloadFiles)` without a single-thread ownership rule ([FileDownloadingControl.cs, lines 12-15](../QuranKareem/DownloadFiles/FileDownloadingControl.cs#L12), [196-203](../QuranKareem/DownloadFiles/FileDownloadingControl.cs#L196), [245-278](../QuranKareem/DownloadFiles/FileDownloadingControl.cs#L245)). `DownloadFiles` is also `async void`. | Possible queue corruption, unobserved failures, and hard-to-reproduce UI errors. Put the queue in a dedicated download service with `Task`, cancellation, and marshalled UI updates. |
| P0 | A download writes directly to its final path. On any exception it deletes that path, including a pre-existing file during a forced download ([FileDownloadingControl.cs, lines 257-269](../QuranKareem/DownloadFiles/FileDownloadingControl.cs#L257)). | A failed retry can lose an existing recitation file. Download to a temporary file, validate it, then replace the target atomically where possible. |
| P0 | Audio description text is concatenated into SQL, followed by `VACUUM` ([AudioQuran.cs, lines 646-651](../QuranKareem/QuranClasses/AudioQuran.cs#L646)). | An apostrophe in a comment can break saving; crafted text can change SQL behavior. Use parameters and separate maintenance operations. |
| P1 | Search reads the entire `ayat` table and normalizes every result inside the button click handler ([TextQuran.cs, lines 589-613](../QuranKareem/QuranClasses/TextQuran.cs#L589), [Form1.cs, lines 728-735](../QuranKareem/Form1.cs#L728)). | The window cannot respond while a search runs, especially with spelling normalization. Move search behind an async/cancellable service and profile an indexed normalized-text strategy. Existing indexes do **not** cover this full-scan substring search. |
| P1 | Page navigation loads a new bitmap, applies pixel edits, and clones it; old `CurrentPicture`/`PagePicture` instances are overwritten without visible disposal ([PictureQuran.cs, lines 353-369](../QuranKareem/QuranClasses/PictureQuran.cs#L353), [372-390](../QuranKareem/QuranClasses/PictureQuran.cs#L372)). | Likely memory and GDI-handle growth during long sessions, along with page-turn latency. | P1 | The verse splitter reads an entire surah into memory and calculates byte offsets from bitrate and timestamps, then copies raw bytes ([AudioQuran.cs, lines 433-454](../QuranKareem/QuranClasses/AudioQuran.cs#L433)). Use format-aware readers/writers and streaming; verify produced files with real players. |
| P1 | Startup and many actions depend on relative `texts`, `pictures`, `tafasir`, `translations`, `libraries`, `splits`, and `videos` paths ([Form1.cs, lines 39-115](../QuranKareem/Form1.cs#L39), [AssemblyResolve.cs, lines 10-20](../QuranKareem/AssemblyResolve.cs#L10)). ## Architecture and maintainability

- `Form1.cs` is about 1,090 physical lines and directly performs startup discovery, navigation, theme changes, playback, search, persistence, timing edits, and export ([Form1.cs](../QuranKareem/Form1.cs)). The button panel even changes from a reciter list into hundreds of timing controls ([lines 392-495](../QuranKareem/Form1.cs#L392), [816-906](../QuranKareem/Form1.cs#L816)). Separate these into focused views/view models and services with explicit state transitions.
- The three visual Quran implementations repeat navigation SQL and maintain their own mutable connection/command/reader fields ([TextQuran.cs, lines 253-358](../QuranKareem/QuranClasses/TextQuran.cs#L253), [PictureQuran.cs, lines 212-317](../QuranKareem/QuranClasses/PictureQuran.cs#L212), [TrueTypeFontQuran.cs](../QuranKareem/QuranClasses/TrueTypeFontQuran.cs)). `IVisualQuran` is a useful boundary, but it still exposes mutable navigation rather than an immutable page/verse result. Unify navigation and data retrieval before changing rendering engines.
- SQLite connections/readers are frequently stored as fields and manually opened/closed. Several startup paths swallow exceptions ([TextQuran.cs, lines 135-180](../QuranKareem/QuranClasses/TextQuran.cs#L135), [PictureQuran.cs, lines 97-168](../QuranKareem/QuranClasses/PictureQuran.cs#L97), [AudioQuran.cs, lines 93-139](../QuranKareem/QuranClasses/AudioQuran.cs#L93)). Prefer short-lived `using` scopes, structured errors, and visible recovery messages. Parameterize queries, especially those built from text or file content.
- UI state is encoded through button text (`"Dark"`, `"إلغاء"`), integer rendering modes (`qPicture`), `Tag`, and guard booleans such as `allow`/`isAllow` ([Form1.cs, lines 172-213](../QuranKareem/Form1.cs#L172), [342-389](../QuranKareem/Form1.cs#L342), [537-645](../QuranKareem/Form1.cs#L537)). Use typed mode/state objects; a label or translation change should not alter program logic.
- No test project or test files were found outside dependencies. Before a large rewrite, add characterization tests for navigation across surah/page boundaries, word mapping, timing edits, downloads, and export formats using small fixtures. This matters because several features depend on unusual verse-zero and word-count conventions explained in the README ([README.md](../README.md)).

## Performance observations to verify with measurements

1. **Interaction runs on the UI thread.** Search, verse splitting, combining, and video image generation are called directly by click handlers ([Form1.cs, lines 728-735](../QuranKareem/Form1.cs#L728), [785-810](../QuranKareem/Form1.cs#L785), [VideoEditorForm.cs, lines 187-225](../QuranKareem/VideoEditor/VideoEditorForm.cs#L187)). Timing and progress reporting should be measured first; long work should run off the UI thread with cancellation.
2. **Navigation fans out into I/O and redraws.** `Ayah_ValueChanged` updates several controls, calls visual `Set`, audio `Set`, and sets a background image ([Form1.cs, lines 593-632](../QuranKareem/Form1.cs#L593)). The Quran classes reopen SQLite and recompute display state. Profile one verse step, one page step, and one word highlight separately before choosing caches.
3. **Controls are recreated in bulk.** Switching reciters clears and rebuilds the button panel; timing mode adds a label, number input, and button for each timestamp ([Form1.cs, lines 455-495](../QuranKareem/Form1.cs#L455), [816-906](../QuranKareem/Form1.cs#L816)). This costs layout and GDI resources. A virtualized list/grid would scale better.
4. **The font renderer identifies its video-generation method as very slow** (`#warning very slow`) and creates an image per word state ([TrueTypeFontQuran.cs, lines 635-692](../QuranKareem/QuranClasses/TrueTypeFontQuran.cs#L635)). Treat export as a pipeline with reuse of rendered lines, progress, cancellation, and output-size limits.

## Product and interface notes

These are design recommendations inferred from the code and designer, not a visual usability test.

- Give reading a clear primary space. Move download management, timing editing, and video export into dedicated screens or dialogs. The current window mixes reading controls with authoring tools and reuses the same side panel for unrelated tasks ([Form1.Designer.cs](../QuranKareem/Form1.Designer.cs), [Form1.cs, lines 392-495](../QuranKareem/Form1.cs#L392), [953-977](../QuranKareem/Form1.cs#L953)).
- Replace fixed pixel positions and `FormSize` scaling with responsive layout containers. The main form is borderless and designed at 1100 x 910; `FormSize` scales only direct child controls and their fonts ([Form1.Designer.cs, lines 1087-1163](../QuranKareem/Form1.Designer.cs#L1087), [FormSize.cs](../QuranKareem/FormSize.cs)). Nested controls and high-DPI behavior need an actual visual check.
- Make interaction labels consistent and self-explanatory. Arabic and English labels are mixed (`Dark`, `Zoom`, `Quran Template`, `Youtube Captions`), and right-clicking a reciter opens downloads without an obvious on-screen cue ([Form1.Designer.cs, lines 962-1082](../QuranKareem/Form1.Designer.cs#L962), [Form1.cs, lines 497-524](../QuranKareem/Form1.cs#L497)). Prefer visible actions, tooltips, and keyboard access.
- Show tafsir, search results, and errors in readable panels. The “quick read” handler currently opens a `MessageBox` and its save-to-RTF code is commented out ([Form1.cs, lines 717-735](../QuranKareem/Form1.cs#L717)). Empty catches and startup failures leave users without a useful explanation.
- Revisit accessible focus order, contrast, minimum size, and RTL layout after choosing the new information hierarchy. The present implementation manually changes colors across a control list ([Form1.cs, lines 339-389](../QuranKareem/Form1.cs#L339)); it needs a centralized theme and visual inspection in both modes.

## Correctness and data risks worth isolating

- `TrueTypeFontQuran.SetCursor` permits `position == pageWords.Count`, then indexes that position or `position - 1`; empty and trailing selections can fail ([TrueTypeFontQuran.cs, lines 568-580](../QuranKareem/QuranClasses/TrueTypeFontQuran.cs#L568)). `TextQuran.SetCursor` returns `true` even when it found no ayah ([TextQuran.cs, lines 513-537](../QuranKareem/QuranClasses/TextQuran.cs#L513)).
- The HTML text highlight is assigned and then immediately replaced by unhighlighted HTML ([TextQuran.cs, lines 375-382](../QuranKareem/QuranClasses/TextQuran.cs#L375)). Check whether this output path is still used before fixing it.
- Tafsir lookup is run in `Task.Run` when right-clicking a verse, while `TafseerQuran` uses a shared connection/command/reader also used by UI handlers ([Form1.cs, lines 660-669](../QuranKareem/Form1.cs#L660), [TafseerQuran.cs, lines 12-21](../QuranKareem/QuranClasses/TafseerQuran.cs#L12)). Concurrent access can collide; the background `MessageBox` is also unowned by the main form.
- Closing writes several separate settings files with no recovery if one write fails ([Form1.cs, lines 216-229](../QuranKareem/Form1.cs#L216)). The `save` path is built by removing the product version from a special-directory string rather than combining a known directory and filenames ([Form1.cs, line 17](../QuranKareem/Form1.cs#L17)).
- A malformed or unsupported database can silently fail initialization because many `catch { }` blocks discard the cause. This is especially important for user-added recitations and images. Add schema validation and an actionable error at import time.
- The delivered content is substantial: roughly 736 files and 290 MiB under `Quran Kareem` in this checkout, mostly tafsir databases and picture/audio assets. Separate source, content packs, and user-generated data for easier builds and updates. Review source rights and attribution before redistribution; the README lists several upstream sources ([README.md](../README.md)).

## Suggested order for a later rebuild

1. Define the intended reading workflow and preserve the existing SQLite content in a documented, validated import format. Compatibility with the current UI and file layout need not constrain the new design.
2. Add a small set of characterization fixtures and record baseline timings for startup, page turn, search, reciter switch, and video export, plus memory/GDI handles during repeated navigation.
3. Extract a read-only Quran repository and navigation model, then separate playback, download, and export services. Give each service explicit ownership of its data and cancellation.
4. Build a simpler reading interface around surah/ayah navigation, recitation, tafsir, and search. Add advanced timing and export tools as separate workflows.
5. Replace risky file operations and audio format handling, then migrate content/settings and validate real outputs before distribution.
